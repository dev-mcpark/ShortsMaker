# Production quality evaluation

This is the repeatable review method for stage 3. [STATUS.md](STATUS.md) owns current findings and stage state. This file defines how to collect the next evidence; it does not claim that an unreviewed video is good.

## Review unit

Keep the source article, final script, rendered video, visual mode, generation settings, and provider charges together in a private local record. Each newly rendered video gets a local `*.production.json` file beside its MP4. The file records the source URL, script key, scene modes/models, generated versus reused/manual scenes, music track and mix level, preflight visual output estimate, quality gate result, finished-file SHA-256, YouTube ID, and AI disclosure choice if uploaded. New successful uploads also retain the prepared private YouTube request body, including title, description, tags, and disclosure, so later review does not mistake an older draft description for the submitted one; older records may omit it. A failed quality check after rendering also gets a record. Runs that stop before rendering do not. For an image-versus-hybrid comparison, use the same script, narration, subtitles, and editing settings; change only the visual mode. Match runs by `script_key` and start with three different topics before drawing a directional conclusion.

An upload creates `*.upload-pending.json` beside the MP4 before calling YouTube and removes it only after the returned ID reaches the production sidecar. It now keeps the prepared private request body alongside the video hash so an uncertain upload can be matched by title and description in Studio. A missing provider response or sidecar write leaves the claim in place. Check the private Shorts list in YouTube Studio before resolving it: save a confirmed video ID in the matching sidecar, or remove the claim only after confirming no upload occurred. The local marker and submitted request body are attempt evidence, not proof that YouTube retained the same metadata or visibility.

For new Veo calls, `outputs/evaluation/visual_attempts/*.json` records each submitted app attempt, including ones that fail before an MP4 exists. It holds model, seconds, output count, preflight output estimate, scene number when known, status, and provider operation/error code when available; it omits the prompt and leaves actual billed USD null. A `timed_out_unknown` or `failed_or_unknown` record is neither proof of a charge nor proof of no charge. Reconcile the provider SKU detail and allocate actual cost to the relevant editorial review separately. Earlier direct pilot attempts remain in their own ignored request files.

For a manually prepared first-frame Veo pilot, keep a tracked visual review record beside the scene brief before requesting motion. Bind the exact spoken scene text, primary and supporting source URLs, first-frame SHA-256, motion-prompt SHA-256, visible acceptance criteria, rejection criteria, and a human verdict. A pending or rejected verdict blocks submission; any changed source, narration, frame, or prompt makes the verdict stale. Review a muted raw clip separately after generation: a good input frame does not prove the movement, factual meaning, or final edit. The [Jamsu scene-3 record](jamsu_scene3_visual_review.json) is the current example. This record captures an editorial judgment and can prevent an accidental stale request; it cannot prove that the image is truthful or authorize a provider charge.

For the ordinary Studio production path, select a video or hybrid scene after confirming the current script. In Generation, supply a local 9:16 PNG/JPEG first frame for each Veo scene, preview it beside the narration, source URLs, visual and motion brief, then write what must appear, what must be avoided, and a review note before approving. The ignored `outputs/evaluation/visual_reviews/` record binds those fields and the exact image bytes to the current script. A changed script, brief, source, prompt version, or frame invalidates the approval; the service refuses new Veo scene work without it. This gate does not create the image, check its factual accuracy automatically, approve the generated raw clip, or grant a new spending limit. A saved first-frame approval is reusable only while its bound inputs remain unchanged.

Generate one Veo scene from its approved first frame, then watch the cached original muted with captions hidden. Record a written approval or rejection in its ignored `clip.review.json` before requesting another scene or starting the whole cut. The saved verdict binds the script, input-frame hash, scene number, and exact MP4 hash; changed footage or script requires a new verdict. A rejected clip stays in the cache for audit and cannot be turned into a finished automatic cut. To try a replacement, change the source-grounded scene brief or first frame, review it again, and obtain a new request budget. The Studio button shows the configured model, seconds, and output-reserve estimate before a new request; clicking it with the paid switch off cannot submit. Approval is a human meaning judgment, not an automatic claim that the clip is factual. Manual clips still rely on separate editorial review.

The one-scene request creates an ignored `request.pending.json` beside the expected clip before calling Veo. It disappears only after a valid MP4 is saved. If the call fails or its outcome is unknown, inspect the matching `visual_attempts` record and provider bill before removing the marker or authorizing another request; the app does not retry this scene automatically. The ordinary image/hybrid pair command also requires approved Veo clips before shared TTS and estimates only new still-image outputs. Include the earlier Veo request when allocating total cost to a story.

The quality sequence for each new story is: source and narration check → visual proof brief per scene → local storyboard or reviewed first frame → separately budgeted visual request → muted raw-clip verdict → complete voice/music/caption cut verdict → private upload for review → separate public-release decision. A failed stage returns only the affected scene or cut to editing. Automatic planning stops with a saved script before narration, visuals, or upload. Studio binds script confirmation to the current script bytes and requires a reviewed local first frame and approved raw clip for each new Veo scene before final narration and edit. Edited text needs another confirmation and new matching visual verdicts. The whole-cut review remains a separate human decision; a valid raw shot alone cannot establish music, caption, pacing, or publication quality.

Manual editorial re-cuts remain in the local evidence but have `paired_comparison_eligible=false` in their sidecar, so a corrected cut with the same script key does not invalidate the original mode pair. Only compare runs where visual mode is the intended difference. The scorecard treats every finished cut outside a unique eligible image/hybrid pair as a standalone editorial review, including a routine automatic upload and ambiguous repeated-mode renders. A cut count is not a count of independent topics. If multiple eligible renders of one script and mode exist, the scorecard skips that ambiguous pair; resolve the run grouping before drawing a mode conclusion.

For a local music/caption review, run `python scripts/creative_review.py BASELINE.mp4 MUSIC_ALTERNATIVE.mp4 CAPTION_ALTERNATIVE.mp4 --output outputs/evaluation/creative_review.html --names BASELINE MUSIC CAPTIONS`. The command requires the baseline and music alternative to have identical encoded video streams and different audio, and the baseline and caption alternative to have identical encoded audio streams and different video. It writes an ignored local HTML page with three video references; open it locally, or open each MP4 in a media player if the browser disallows local-file pages. This proves which encoded stream changed, not that playback works in every browser, music fits the story, captions look good, source claims are correct, or a cut is publishable. Leave the private review CSV unaccepted until the owner judges the complete videos.

For two or more music-only options, run `python scripts/music_review.py --cut '무음 기준' BASELINE.mp4 --cut '곡 A' MUSIC_A.mp4 --cut '곡 B' MUSIC_B.mp4 --output outputs/evaluation/music_review.html`. It rejects a changed video stream or repeated audio stream before writing the private page. Use the same script, narration, clips, subtitle style, and mix level for the rendered cuts; stream equality alone cannot prove those production choices or musical fit. Keep `accepted` blank until listening review.

After verifying a script against its source and approving each hybrid Veo raw shot, run `python scripts/paired_review.py path/to/script.json --budget-usd 1.25`. The command checks a conservative upper estimate for new image outputs before TTS, refuses a missing or stale raw-shot verdict, creates one narration set, and renders image then hybrid with that same audio. It produces local videos only and never submits a new Veo request. Its estimate can double-count images later reused from the scene cache; actual provider charges may also include other calls outside this command.

## Record for each video

| Check | What to record |
| --- | --- |
| Technical gate | Narration-file signal preflight, `check_video_quality` result, duration, width × height, audible narration in the final mix, final audio loudness, visible scene defects |
| Source accuracy | Each concrete number, quote, named entity, causal claim, and past-tense event checked against the primary source; distinguish an assigned role or capability from an observed result and count unsupported claims |
| First five seconds | Whether the opening states a specific reason to keep watching without a generic intro |
| Story turn and payoff | A source-supported dilemma, the actual decision or result revealed early, and a clear conclusion; reject a chronological list of facts without a turn |
| Narration and pacing | Intelligibility, awkward speed changes, pauses, phrase caption timing, one-word orphan captions, whether text reveals a later fact early, and dark frames at scene cuts |
| Visual relevance | Before spending, state the source-backed relationship the viewer must **see**, plus which part comes from Veo and which from the editor. After rendering, watch silently with captions hidden: can the relationship be inferred from shapes and motion, rather than only read as labels? Check setting, counts, roles, invented marks, and whether AI illustration is distinguished from actual footage. |
| Visual rights | Original source and credit for each photo or clip, publisher usage terms and any third-party exception, recognizable people or protected logos, and whether the video implies an agency's endorsement |
| AI disclosure | Check whether any AI-generated or altered scene appears photorealistic or changes a real event/place. Record the YouTube AI-use choice and verify it before publication; obvious diagrams and script assistance alone do not require disclosure under [YouTube's guidance](https://support.google.com/youtube/answer/14328491?hl=en). |
| Visual rhythm | Distinct composition or meaningful motion across scenes; note repeated photos and static stretches even when every individual frame is accurate |
| Music | Compare the script's `music_direction` with the selected track and the full rendered scene arc by ear; record whether the bed is audible under speech, avoids masking narration, and has documented rights for publication. Intentional silence needs an editorial reason. |
| Channel distinctness | Before publication, compare the cut and its title/description with the channel's recent and most-viewed videos. Record the source-backed question, creator explanation, and visual evidence that make this episode meaningfully different; reject a cut whose story and visuals are interchangeable with another episode. This is a manual channel-level review under [YouTube's monetization policy](https://support.google.com/youtube/answer/1311392?hl=ko), not a guarantee of YPP eligibility. |
| Cost | Sidecar's preflight visual output estimate, actual provider charge attributable to the run, rejected generations, and production time |
| Outcome, if published | Video ID, publish date, retention and revenue after a consistent observation window |

Do not publish a video with a failed technical gate or an unsupported factual claim. Resolve the defect, regenerate only affected scenes when possible, and repeat the check. Human reviewers decide whether hook, narration, and visuals are good enough; the current code does not score these reliably.

## Comparison and sharing

Compare image and hybrid by accepted-video rate, actual cost per accepted video, and reviewer notes first. Standalone cuts, whether automatic or manually edited, are summarized separately from unique image/hybrid pairs, including rejected drafts when their costs are assigned. The sidecar estimate is not the provider bill: it excludes prompt tokens, narration, retries, taxes, and any charges from a failed run without a rendered video. Reconcile bills separately in the private record. Use retention and revenue only after the same observation window and enough published samples. Do not infer audience preference from the nine legacy files in the technical baseline: they were not paired experiments and have no sidecars. Keep raw articles, bills, channel metrics, sidecars, and video files outside Git. Share only anonymized counts, aggregate costs, findings, and resulting code decisions in `STATUS.md` or `DECISIONS.md`.

Run `python -m shorts_maker.services.scorecard init` after each new render to add missing rows to the ignored `outputs/evaluation/reviews.csv`. Fill `accepted` with `yes` or `no` after the checks above; mark superseded editorial drafts `no` and the chosen cut `yes` only after full review. Enter `billed_cost_usd` from the private provider records, including failed attempts and a consistent allocation of shared narration/planning cost. The optional `views_7d`, `average_view_duration_seconds_7d`, and `revenue_usd_7d` refer to the same first seven days after each public upload; leave them blank until observed. Run `python -m shorts_maker.services.scorecard summary` for paired acceptance, separate editorial-cut acceptance/cost, distinct-primary-source story cost, paired seven-day outcomes, and accepted editorial-cut seven-day outcomes. `source_stories` groups all rendered cuts, including comparison pairs and revised scripts, by the exact recorded primary `source_url`; a group counts toward cost only when **every** cut has an editorial verdict and allocated bill. Its `accepted` counts each such source once if any cut is approved, while `unattributed_cuts` reports records without a source URL. One URL is only a proxy for a story; different sources can cover the same event, and revisions without a rendered sidecar or separately billed failed attempts must be allocated manually. Editorial retention can be summarized before the bill arrives; cost per accepted video or source story still waits for allocated billed cost. A YouTube ID proves an upload, not public visibility: enter outcome values only from a verified public video's seven-day window. A revenue total stays blank until every included editorial video has a revenue value. The current YouTube token only grants upload access, so these metrics must be entered from a private export until analytics read scopes are authorized.

`scorecard init` adds the `public_release_confirmed` column to an older private CSV while preserving its existing review entries. Leave it blank for private or pending videos. After the owner separately approves publication and YouTube shows the video as public, enter `yes` in that video's row; use `no` for a video that will remain private. Paired and editorial seven-day summaries require `yes` as well as an upload ID and the two observed retention fields. This is an operator attestation, not an API visibility check. Record the first complete seven-day window only after it has elapsed.
